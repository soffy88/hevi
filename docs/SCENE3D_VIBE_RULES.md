## §03 生成之后：验收与读数

- **读数三件套**：Topology（Quad/Triangle）、Faces、Vertices。资产入管线时第一件事
  就是把这三个数读出来写进清单，不看图下结论。我们的 `assets_pipeline` 用 GLB 头
  直接算，不经过任何引擎。
- **验收要在中性条件下**：夜景、低角度、贴很近会让低模退化成剪影，把「资产没问题」
  误判成「重建失败」。我们的资产预览固定用中性光 + 正面 + 退到整体入画的机位。
- **批量后别再一张张点预览页**：改成固定机位批量渲图一次看完。对应我们的
  `validate` 阶段批量出 `contact sheet`。
- **朝向必须逐件定，不能靠推理**：四视图分不出正/背面，建筑四个立面也像。要渲
  六视图（−Z/+X/+Z/−X/顶/斜45°）看「哪一格看见正脸」。包围盒帮不了：yaw±90°
  包围盒完全一样。我们把它落成 manifest 里的 `yaw_deg` 字段 + 六视图证据。
- **导出这一步不额外收费**（余额前后不变，实测），所以「降贴图档」是白拿的。

## §04 减面与重拓扑

- **先数面数，再决定动不动拓扑**。巴黎那批 29 件独立资产面数 16711–46196、
  中位数 18509，**没有一件超 10 万**，整条项目一次重拓扑都没用上。
- **面数上限的两种口径**：智能网格的 `face_limit` 数的是**四边面**，高精度模型数的是
  **三角面**。同一个 8000 填进去，四边面那侧三角化后是 15431，几何预算是三角面那侧
  的 **2.09 倍**（E10 实测）。
- **四边面→三角面换算系数 = 1 + 四边形占比**，实测落在 **1.75–1.8**，不是 2。
  按 2 排预算会系统性高估约 10%（把本来塞得下的东西砍掉）。
  - E10 B件：8596 面、四边形 79.51% → 1.795，实测 15431÷8596=1.795。
  - P2.0 出租车：5615 面、四边形 74.5% → 1.745，实测 9800÷5615=1.745。
- **减面下限由几何光滑度决定**（E1，11 件实测，`gltf-transform simplify`）：

  | 类别 | 原始面数 | 减面下限 | 下限占比 |
  |---|---:|---:|---:|
  | 人物 pedestrian-01 | 19042 | 629 | 3.3% |
  | 人物 pedestrian-05 | 18542 | 1450 | 7.8% |
  | 载具 car-01 | 18083 | 1633 | 9.0% |
  | 道具 prop-02-bench | 16320 | 1526 | 9.4% |
  | 道具 prop-cafe-shop | 17653 | 5648 | 32.0% |
  | 建筑 building-01 | 17043 | 6258 | 36.7% |
  | 建筑 building-03 | 16696 | 6783 | 40.6% |
  | 建筑 haussmann(重拓扑后) | 41106 | 18270 | 44.4% |
  | 地标 eiffel-tower | 19424 | 14087 | 72.5% |
  | 植被 tree-01 | 7473 | 7123 | 95.3% |

  规律不在类别，在几何：连续曲面砍得狠（人体 3.3%），直角窗洞栏杆砍不动（建筑 37–44%），
  格构/分离薄片几乎砍不动（铁塔 72.5%、树 95.3%）。
- **生产参数要留余量**（E2 实跑用的值）：人物/载具/道具 0.25，建筑 0.45，树/铁塔 0.75。
  **不要一套参数跑全库**：统一 0.25 会毁掉建筑细节，对人物又太保守。
- **分类不能只看文件名**：`prop-03-planter` 名字是道具、几何像小建筑，按 0.25 只减到
  7652 面。跑完要回头核面数对不对。
- **命令口径**（我们本地装 `@gltf-transform/cli`，不走 npx 每次启动开销）：

  ```bash
  gltf-transform simplify in.glb tmp.glb --ratio 0.25 --error 1
  gltf-transform optimize tmp.glb out.glb --compress quantize --texture-size 512
  ```

  `optimize` 子命令里的 `--simplify` 对某些资产不生效（树，§17 坑一），必须用独立
  `simplify` 子命令且带 `--error`。
- **面数预算的正确次序：先量 GPU 耗时和绘制调用，量不出问题就别动面数**。手册里跑得
  最重的 demo 是 244 万三角面、77 draw call、渲染一帧 5.0 ms（vsync 预算 16.7 ms，
  还剩三倍余量）。**瓶颈是贴图和 draw call，不是三角面**。
- **单件面数分配**（够用的起点）：主角/特写 1.5–2 万；中景道具 5 千–1 万；远景/实例化
  1 千以内或程序化。
- **重拓扑的代价**：奥斯曼建筑压到 2 万面后，镂空阳台栏杆糊成一团，细节只能靠贴图补。
  纯几何层面 2 万面撑不住装饰性结构。
- **减面之前先去量贴图**：小王子星球卡顿的真凶是 31 张贴图 5.0 GiB 显存，GPU 只忙
  0.37 ms。直接减面/关泛光/砍阴影画质掉一大截，问题原封不动。

## §05 智能拆分与贴图生成

- **AI 生成网格是「一层壳」，不是「一个装配体」**。Blender `separate(type='LOOSE')`
  把一辆车切成 **358 块** 100–650 面的碎片：轮子和车身在几何上糊在一起，连通分量这把
  刀切不到缝。这条同时解释了 §06 的自动权重为什么会塌——**根因是同一个**。
- **语义分件**（按「这块是什么」分）才给出有意义的零件，前提是**三角面、未绑骨**。
  工序顺序：**拆在前，绑在后**。
- **同几何多贴图**：几何零改动（17366→17366 面、14265→14265 顶点），换一张贴图变体
  就能消重样。引擎里还能共享几何省显存。API 层对应固定 `model_seed`、只改
  `texture_seed`。
- **P2.0 出的贴图只有一张 base color**，没有 normal / ORM，同灯下会比三图版本哑一点。
  进 Three.js 时要么接受，要么在引擎里补材质参数。

## §06 绑骨与动画

- **入口省 50 积分的判据**：模型本来就在账号里就直接选，别下载再传回去（上传收
  50 导入费，还会弹「找到最佳角度」）。我们对应的是：**资产本地登记，不重复导入**。
- **能绑骨的承重判据是四条，不是「必须 T-Pose」**：全身入画、正视角、**手臂与躯干有
  空隙**、两腿分开站稳。核心那条是**空隙**——四肢糊在躯干上算法分不出胳膊和身子。
  A-Pose（手臂下斜 30–40°）只要分得开一样能过（19 秒一次成）。
- **导出「没有动画」不是丢了，是分成两个文件**：
  - `tripo_rigging_*.glb`：网格 + 41 关节骨架，**没有动画**；
  - `tripo_retarget_*.glb`：骨架 + `preset:biped:walk`（126 通道），**没有网格**。
  两个同源、41 关节同名，`AnimationMixer` 按节点名字绑轨道对得上。
  - `tripo_retarget_` 没有 `_meshopt` 后缀，可离线直接读；带 `_meshopt` 的读出来是乱码。
- **一条资产里可能带两条动画，第一条是空的**（P2.0 绑骨件）：
  `Armature.001|Armature|ArmatureAction`（空）和 `...|preset:biped:walk`。
  **不要用 `animations[0]`**，要按名字挑：`/walk/i.test(a.name) || a[0]`。
- **动画数据形状**（巴黎西装行人实测）：123 个通道 = 41 关节 × 3（位移/旋转/缩放），
  其中 **16 个通道带关键帧**（真正在动的腿/臂/脊柱，帧数 51–57），采样间隔
  **0.042 s（约 24 fps）**，时长 **2.375 s** 一个完整走路循环；其余 107 个是常量通道
  （手指等不动关节，正常结构）。面数从头到尾没涨（19830 进、19830 出）。
  - 41 关节、只有关节带通道 = 123 通道；连骨架根节点也带通道 = 126 通道（小王子那件）。
- **接进引擎的三条硬约束**：
  1. 用 `SkeletonUtils.clone()`，**不要普通 `clone()`**（会共享骨骼，一排人同手同脚）。
     `SkeletonUtils.js` 不在精简 vendor 目录里，缺了会整页白屏，报错指向模块解析。
  2. 每个实例一个 `AnimationMixer`，**相位错开**：`(x*0.37 + z*0.11) % duration`。
  3. **切掉位移轨，只留旋转轨**。`Hip.position` 的 Y 位移范围 1.338，而人本身才 1 米
     出头；位移归代码管，动画再叠一层位移循环回到起点会往回弹一大步。
- **别呆的小设置**：`mixer.timeScale` 跟着实际移动速度走（按 2.5 m/s 定标），站住时冻住。
  不做会有「脚在原地小碎步、人在飞速平移」的滑冰感。
- **朝向惯例按来路分三套，混着记必然装反**：

  | 这一类 | 自身正面朝哪 | 处理 |
  |---|---|---|
  | Tripo 绑骨预设人形 | 不是 +Z，实测差 90° | 写死 `yaw = -π/2` |
  | 高精度 v3.1 静态资产 | 行人 **+Z**、建筑 **−Z** | 同批里两套，分开定 |
  | 智能网格 P2.0 家族 | **+X**（38 件里 36 件如此） | 顶替旧行人 `yaw=-90`、旧建筑 `yaw=+90` |

  两个例外只能渲图看：某车正面在 −X，某书箱正面在 −Z。
- **量绑骨模型身高比想的难**（三处叠加的错）：量的是世界 Y 极值（摆到球面上人就斜了）；
  `bindMatrixInverse` 陈旧（three.js 只在 `updateMatrixWorld()` 里刷，而 `SkinnedMesh`
  重写的正是这个方法）。正解：**沿角色自己的上轴投影，且先
  `updateWorldMatrix(true,true)` 刷祖先链、再 `updateMatrixWorld(true)`**。
  最省事的验法是把它和一个已知尺寸的东西放进同一张图里看一眼。
- **批量做角色先按件数算账**：游乐园 44 个行人若每个单独生成+绑骨 = 3080 积分。
  更划算的是做 3–5 个不同外观，其余靠**实例化 + 随机相位**错开。

## §17 生成与清洗流水线

- 四步：**设计图 → 逐件生成 → 导出 GLB → 批量减面 → 归一化尺寸**。真正吃时间的是
  第一步排队，不是后面的处理（25 件批量清洗实测 131 秒、平均 5.2 s/件）。
- **导出时就把贴图降下来**：默认 8192²，17 件实测吃 5.0 GiB 显存；降到 1024² 是
  0.22 GiB，游戏视距下肉眼无损。
- **批量降贴图可以不开 Blender**：直接改 GLB 里的 glTF JSON 与 BIN 块，只动 images
  那几段字节。好处是「三角面不变、包围盒不变、扩展依赖不变」**构造上就动不了**。
  38 件实测：534.6 MB → 52.4 MB（9.8%），合计三角面 735232 → 735232 **逐件相等**，
  贴图 8192² → 1024²（q92、不做色度抽样）。
  - 多张贴图时**按原图名一一对应地换**，不要「把所有槽位换成第一张图」——那会把法线图
    也替成颜色图，而这个错渲出来还挺好看，不看文件发现不了。
- **`doubleSided` 静默翻倍**：Blender FBX 导入器默认不开背面剔除，导出到 glTF 就成了
  双面，片元开销翻倍，**画面上没有任何症状**。批量转完要统一强制单面（薄片类资产
  如招牌/树叶单独开）。
- **归一化尺寸的契约**：`y=0` 落地、整体高度归一到 1 个单位，之后由引擎按真实米数缩放。
- **缩放基准别习惯性选整体高度**：GLB 树宽高比≈1:1，程序化树是「宽 8 高 11」的瘦高个，
  按整树高度放大 → 冠幅 14 m 而树间距只有 8 m，整排树糊成一堵绿墙。**按那个「和邻居
  对齐」的维度归一**：行道树按冠幅、建筑按临街面宽度、人物按身高。
- **包围盒一样、几何不一样**（同一个坑的第二种长法）：新咖啡套件多了一根 2 m 伞杆，
  按包围盒总高归一后桌椅从 1.1 m 掉到 0.5 m。判据：**量顶点高度分布，p90 明显低于
  0.7 说明包围盒高是被细杆/天线/伞撑起来的**，不能拿总高做归一基准。一行代码就能算。
- **树那类资产几乎砍不动**：18414 面用 meshoptimizer 最多减到 7473，ratio 0.1 和 0.05
  结果完全一样，再减破坏分枝拓扑。而且**三角面预算会爆**：全城 2 万株程序化树只占
  9 draw call、8.4 万三角；换成 15k 三角的 GLB 树，光近景 150 株就是 225 万三角，
  是整层预算的 26 倍。折中：近景少量 GLB、中远景继续程序化。
- **转换器自己的读数不能当证据**：FBX→GLB 时同时跑三条互不相干的通道量同一个包围盒
  （纯 Python 解 FBX / Blender 侧读世界包围盒 / 解产物 GLB），最大偏差 1.0e-08。

## 附B 踩坑索引（按症状，只留与 CPU 渲染/Three.js 有关的）

| 症状 | 根因 | 修法 |
|---|---|---|
| 白底下模型渲成一片死黑 | Tripo PBR 金属度高、漫反射被抑制，场景没有环境贴图 | canvas 画带暗部的渐变当 equirect，走 `PMREMGenerator` 挂 `scene.environment`；**别开 ACESFilmic 色调映射** |
| 整个画面发白、没有重量感 | 环境贴图从白到浅灰，金属反射全是亮色 | 给环境贴图一块暗部（摄影棚黑旗） |
| 模型被放大到画面里只剩两只鞋 | `Box3.setFromObject` 量 `SkinnedMesh` 不准——包围盒缓存不会自己更新 | 直接读 GLB 里 `POSITION` accessor 的 `min`/`max` 拿真实尺寸 |
| 一排角色像仪仗队、动作完全同步 | 带 skeleton 的模型用普通 `clone()` 共享骨骼 | `SkeletonUtils.clone()` + 相位 `(x*0.37+z*0.11)%duration` |
| 改了 `material.transparent` 没反应 | 需要重新编译 shader | 加 `needsUpdate = true` |
| 自建几何一旋转就被甩变形 | 形状是相对别的参照点定义的 | 先移到支点再旋转，形状在自己的局部坐标里画 |
| 拖了滑块没反应，像交互坏了 | 异步竞态，模型还没加载完 | 所有模型 load 完后把当前控件值补应用一次 |
| 后台标签页截图拿到旧画布 | `requestAnimationFrame` 在隐藏页被暂停，Chrome 还密集节流定时器 | 本地自校验加 `setInterval(frame,340)` 兜底；自动化截图直接走无头 Chrome |
| 两个零件互相穿进去 | 把有几何约束的两个量当独立参数各设一条曲线 | 先找出约束方程，其余参数从它推出来 |
| 某个零件还没装，画面上却已经飘着 | 独立 mesh 没归进任何一件 | 凡是 `scene.add` 的东西都要有归属 |
| 连调四轮材质都「还是发白」 | 页面加载遮罩没淡出，盖在整个画面上 | 截图自校验前先确认遮罩消失；整体发白且各元素受影响一致，先查覆盖层 |
| GLB 加载被 CORS 挡住 | 页面用 `file://` 打开 | 起 `python3 -m http.server`（我们的渲染器本来就走本地 http） |
| 同一个 GLB 这个工具量 1 米、那个量三万多米 | 用了 `KHR_mesh_quantization`，顶点是 `normalized:true` 的 int16，不认这个标志的解析器把整数当世界坐标 | 按分量类型归一化再读；出现 32767 或它的倍数就是这个 |
| 近处的树凭空消失，远处好好画着 | 实例池配额满了就**整棵不画**，没有降级分支 | 抢不到近景坑位就退到远景池画简化版，不是不画；配额调大几乎不花钱 |
| 帧时间方差大得离谱 | 另一条命令行在用无头浏览器抢同一块 GPU | **量性能前先确认没有别的进程在用 GPU**，同时只渲染一个 |
| 离线解析 GLB 读出来是乱码 | CDN 上拿到的是 `_meshopt` 压缩变体 | 先 `gltf-transform copy` 解开；`tripo_retarget_` 没有这个后缀可直接读 |
| 模型渲出来一模一样，片元开销却翻倍 | `use_backface_culling` 语义是反的，不开它导出的 glTF 就是 `doubleSided:true` | 导出前设 `mat.use_backface_culling`；**不看 GLB 的 JSON 发现不了** |

> 这五张表里出现频率最高的一类是**「报错不发生、程序不崩、画面看着也对」的静默错误**。
> 共同解法只有一条：**把关键量打印出来对账，别靠看画面下结论。**

## 落到 Hevi scene3d 的操作清单

1. 资产入管线先**读 GLB 头**数三角面/顶点/贴图尺寸/体积/骨骼/动画剪辑，写进 manifest。
2. 减面**按几何类型分配比例**（0.25 / 0.45 / 0.75），**贴图降到 512 或 1K**，缓存结果。
3. 单帧渲染时间要有**预算门**：SwiftShader 下逐帧计时，超预算就拒绝出片。
4. 角色用 `SkeletonUtils.clone()` + 每实例一个 `AnimationMixer` + 相位错开 + 切位移轨，
   由 `window.__setTime(t)` 确定性驱动（不依赖实时时钟）。
5. 朝向逐件写死 `yaw_deg`，六视图留证。
6. 相机/主光/轮廓清晰度按幼儿向模板统一。
7. 关键量打印对账：面数、贴图尺寸、单帧耗时、sha256。
